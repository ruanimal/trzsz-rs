# trzsz-rs 与 trzsz-go 文件传输性能记录

测试日期：2026-10-28。以下结果用于记录本次实验，不代表所有设备或网络条件下的性能。

## 测试环境与方法

- 主机：macOS Darwin 24.6.0，arm64；使用同一台机器的本地文件系统和进程管道。
- Rust：trzsz-rs 1.3.0，提交 `d66a4c8e1798ed0b316074f520e9973164a68885`，`rustc 1.99.1`，使用 `cargo build --release --locked` 构建；项目的 release 配置使用 `opt-level = "z"`、LTO 和单 codegen unit。
- Go：仓库内 trzsz-go 1.2.0，提交 `4432ed0e72daac44930bf771c7fd61ab197df08e`，使用 Go 1.26.3 的默认 `go build` 构建。接收端固定为相同版本的 Go `TrzszFilter`。
- 测试的是 `tsz` 发送方向：分别运行 Rust 和 Go 发送端，经进程管道连接到同一个 Go 接收端；未启用 tunnel。实际协商协议为 4。该结果不能直接代表 `trz` 上传方向或两端全部由 Rust 实现的性能。
- 使用随机数据；除注明非二进制模式的测试外，均使用 `-b -c no -q -y`。每次运行先删除目标文件，完成后检查源文件和接收文件的 SHA-256 一致。
- 耗时从发送进程启动到退出，包括启动、协议握手、文件处理和结束流程。吞吐量按原始文件大小除以完整耗时计算，单位为 MiB/s；`K`、`M` 均按 1024 进位。
- 测试顺序以固定随机种子打乱。文件可能已被系统缓存，结果包含本机调度、文件系统和管道的影响。没有测试真实 SSH、终端或远程磁盘。

## 不限速的本机管道

32 MiB 文件，每组测三次，表中为吞吐量中位数。非二进制模式同样使用 `-c no`；它不是默认 `-c auto` 的性能结果。

| 模式 | `-B` | Rust MiB/s | Go MiB/s |
| --- | ---: | ---: | ---: |
| 二进制 | 1K | 6.81 | 35.35 |
| 二进制 | 64K | 42.07 | 41.42 |
| 二进制 | 1M | 44.05 | 46.60 |
| 二进制 | 10M | 43.13 | 39.90 |
| 二进制 | 64M | 42.85 | 44.82 |
| 非二进制 | 64K | 22.46 | 19.70 |
| 非二进制 | 10M | 24.80 | 23.89 |

本机波动较大。例如 Rust `1K` 三次分别为 7.940、4.700、1.454 秒；稍后的参照测试分别为 1.037、1.157、1.055 秒。因此不能把不同批次的小幅差异解释为稳定的性能差异。在第一批次中，二进制 `64K` 到 `64M` 没有显示出稳定的优势区间；二进制模式在本次随机数据上明显快于非二进制模式。

### 补测 64K 以下

同一 32 MiB 文件和二进制模式，每组测三次。`2K` 至 `32K` 为补测批次，`1K` 和 `64K` 是随后重测的参照，表中为中位数。

| `-B` | Rust 耗时（秒） | Rust MiB/s | Go 耗时（秒） | Go MiB/s |
| ---: | ---: | ---: | ---: | ---: |
| 1K | 1.055 | 30.34 | 0.651 | 49.14 |
| 2K | 0.853 | 37.50 | 0.656 | 48.76 |
| 4K | 0.754 | 42.45 | 0.656 | 48.80 |
| 8K | 0.712 | 44.95 | 0.651 | 49.17 |
| 16K | 0.697 | 45.93 | 0.642 | 49.84 |
| 32K | 0.691 | 46.31 | 0.641 | 49.93 |
| 64K | 0.671 | 47.69 | 0.641 | 49.91 |

参照批次也重测了 `4K` 和 `16K`：Rust 分别为 0.759 和 0.700 秒，Go 分别为 0.647 和 0.641 秒。虽然与补测批次接近，跨批次比较仍应注意本机波动。

## 模拟带宽与延迟

通过进程管道中的字节流代理模拟链路，未修改系统网络配置。双向分别按 **625,000 字节/秒（5 Mbit/s）**限速，每个方向再添加 50 ms 固定延迟，基础往返延迟约 100 ms。代理按读到的数据块进行计时和转发，保持字节顺序；分块、调度和背压也会影响实际耗时。

该模型没有模拟丢包、抖动、TCP 重传、拥塞控制或真实 SSH，不能代表所有弱网。仅比较 `64K` 以下的配置。所有测试使用二进制模式且关闭压缩。

### 256 KiB 文件

每组测三次，表中为耗时中位数，包含握手与结束流程。

| `-B` | Rust（秒） | Go（秒） |
| ---: | ---: | ---: |
| 1K | 6.532 | 1.820 |
| 2K | 3.893 | 1.821 |
| 4K | 2.553 | 1.822 |
| 8K | 1.976 | 1.830 |
| 10K | 1.891 | 1.822 |
| 16K | 1.743 | 1.811 |
| 32K | 1.681 | 1.909 |

### 1 MiB 文件复核

每组测两次，表中为平均耗时；两次结果也保留在表内，避免把少量样本解释为稳定性能。

| `-B` | Rust 平均（秒） | Rust 两次（秒） | Go 平均（秒） | Go 两次（秒） |
| ---: | ---: | --- | ---: | --- |
| 1K | 22.516 | 22.459、22.573 | 3.485 | 3.469、3.501 |
| 4K | 6.788 | 6.796、6.781 | 3.402 | 3.497、3.307 |
| 16K | 3.248 | 3.248、3.248 | 3.082 | 3.076、3.089 |
| 32K | 2.939 | 2.928、2.949 | 3.181 | 3.175、3.186 |

这一模拟条件下，Rust 从 `1K` 增大到 `32K` 显著缩短了耗时。Rust 协议 2 及以上的发送实现允许最多 5 帧待确认：以 `1K` 帧和 100 ms 往返延迟粗略估算，确认窗口对应约 50 KiB/s；1 MiB / 22.516 秒约为 45 KiB/s。此估算忽略了协议、处理和排队开销，只用于解释数量级。

## `-B` 与实际帧大小

两种实现的默认 `-B` 都是 `10M`，它是分块大小上限而非固定块大小。协议 2 及以上的实现根据确认耗时动态调整；Rust 的初始值为 10 KiB，并限制到配置上限，同时内部最大帧限制为 64 MiB，见 [v2.rs](../src/v2.rs)。

本次对数据帧的额外抓取显示：Rust 的 `2K`、`4K`、`8K` 配置分别发送对应大小的帧；Go 的 `1K`、`2K`、`4K`、`8K` 配置仍发送 10 KiB 帧。Go 的 `16K` 和 `32K` 则从 10 KiB 增长到相应设置值。原因与 Go 初始缓冲区为 10 KiB、增长时才检查配置上限有关，见 [transfer.go](../trzsz-go/trzsz/transfer.go) 和 [pipeline.go](../trzsz-go/trzsz/pipeline.go)。这是本次所测提交的行为；小于 10 KiB 时，两者同名 `-B` 参数没有产生相同的帧大小。

## 使用结果时的注意事项

- 普通本机测试中，保留默认 `10M` 是合理起点；本次没有证据表明 `64M` 一定更快。
- 在本次 5 Mbit/s、100 ms 的模拟链路上，Rust 的 `32K` 优于更小的配置；Go 在 `16K`、`32K` 附近的结果相近。不能据此推断其他链路的最优值。
- 测试使用随机数据和 `-c no`；默认 `-c auto`、可压缩文件、大文件、多文件、真实终端及高丢包网络可能有不同结果。
- 该记录只覆盖固定 Go 接收端的发送测试和一组模拟链路，不应据此给 Rust 或 Go 做通用性能排名。
